# Malware Analysis Report

### Summary
The analyzed code snippets reveal a sophisticated mechanism designed for **Information Theft** and **Dynamic Code Execution/Evasion**. The application collects sensitive metadata regarding its own installation (package name and APK file path) and passes this data to native methods. Furthermore, it employs a dynamic loading pattern where a `BroadcastReceiver` acts as a proxy to instantiate and execute code loaded from a custom class loader, wrapping the execution within native calls to potentially obfuscate the control flow and evade detection.

**Identified Malicious Behaviors:**
*   **Information Theft (Metadata Exfiltration):** `com.secapk.wrapper.Util.tryDo` collects the application's package name, APK source directory, and process name, passing them to a native method `r2` in `com.secapk.wrapper.ACall`.
*   **Dynamic Code Loading & Proxying:** `com.slpresent.LMR.LMR` uses a custom class loader to dynamically instantiate a `BroadcastReceiver` and executes it within a wrapper of native calls (`c1` and `c2`) from `com.secapk.wrapper.ACall`.

---

### Detailed Analysis

**com.secapk.wrapper.Util.tryDo**
`com.secapk.wrapper.Util.tryDo` retrieves the application's package name, the absolute file path of the APK (`sourceDir`), and the current process name. These three pieces of information are then passed as byte arrays to the native method `r2` located in `com.secapk.wrapper.ACall`. This behavior is highly suspicious as it gathers environmental identifiers that are often used by malware to identify the target environment or to prepare for exfiltrating the APK itself.

**com.secapk.wrapper.ACall.r2, c1, c2**
`com.secapk.wrapper.ACall.r2`, `com.secapk.wrapper.ACall.c1`, and `com.secapk.wrapper.ACall.c2` are all declared as `native` methods. This indicates that the actual logic for handling the stolen metadata (`r2`) and the proxying/monitoring of the dynamically loaded receiver (`c1` and `c2`) is implemented in compiled C/C++ code (JNI). This is a common technique used to hide malicious logic from static Java analysis tools.

**com.slpresent.LMR.LMR.onReceive**
`com.slpresent.LMR.LMR.onReceive` implements a dynamic proxy pattern. It attempts to obtain a custom class loader via `com.slpresent.Util.getCustomClassLoader()`. If successful, it uses this loader to load a class and instantiate it as a `BroadcastReceiver`. Once the `realReceiver` is instantiated, the code calls `com.secapk.wrapper.ACall.getACall().c1(...)`, then executes the receiver's `onReceive` method, and finally calls `com.secapk.wrapper.ACall.getACall().c2(...)`. This structure is designed to hide the execution of the dynamically loaded component behind native method calls, making it difficult for security analysts to trace the actual intent of the loaded code.
